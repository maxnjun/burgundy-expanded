# 온라인 저장 및 재접속 복구

## 저장 경계

온라인 상태의 기준은 서버다. `RoomStore`는 각 요청에서 방을 저장소에서 읽고, 엔진 검증을 통과한 상태를 저장한 뒤 응답한다. Render에서는 `BURGUNDY_STORAGE=upstash`와 기존 `staging` 네임스페이스를 그대로 사용한다. 로컬 JSON을 Render의 영구 저장소로 사용하지 않는다.

기존부터 저장되는 데이터는 `StoredRoom.game` 전체(주사위·사용 여부·턴·단계·라운드·개인 영지·공용 공급·저장고·자원·상품·점수·방패·포도밭·무역로·여관·추가 효과·난수 seed/cursor), 좌석 토큰 해시, Undo 기록, 시작 성 미리보기, 로비와 영지 후보다. 메모리의 이벤트 버스·잠금·읽은 revision 캐시는 알림과 최적화용이며 복구 원본이 아니다.

## 행동 확정과 중복 방지

클라이언트는 행동 전송 전 `requestId`, 원래 `revision`, 행동 본문을 같은 브라우저의 `burgundy-online-action:<roomId>` 키에 저장한다. 요청에는 기존 Bearer 좌석 토큰을 사용한다. 준비/프로필·영지 선택·일반 행동·Undo도 동일한 전송 경로를 사용한다.

서버는 방 JSON의 선택 필드 `requests`에 요청 ID·좌석·본문 해시를 기록한다. 이 기록과 변경된 게임 상태는 기존 Redis Lua CAS의 한 `SET`에 함께 포함된다. 기존 revision과 일치한 경우에만 저장하므로 다른 서버 프로세스와 경쟁해도 덮어쓰지 않는다. 기록은 GameState/Undo 스냅샷 밖에 있어 되돌리기로 지워지지 않는다.

- 같은 좌석의 같은 요청 ID와 본문은 행동을 다시 실행하지 않고 최신 공개 뷰를 반환한다. 원래 응답 뒤 상대가 행동했어도 이전 뷰로 되돌리지 않는다.
- 같은 ID에 다른 본문을 넣거나, 다른 사람의 행동을 실행하거나, 다른 요청이 먼저 확정된 revision을 쓰면 거부한다.
- CAS 충돌 또는 Redis 응답 유실 시 다시 읽어 같은 요청의 확정 기록이 있으면 그 결과를 인정한다. 없으면 성공으로 가장하지 않는다.
- 최근 128개 확정 기록만 유지한다. 오래된 기록이 제외돼도 원래 요청의 이전 revision은 거부되므로 재실행되지 않는다. 오래된 요청에 대한 성공 응답 재현까지 무기한 보장하는 것은 아니다.
- 네트워크 오류·503·429에서는 미확인 요청을 보존하고 1·2·4·8초 이후 최대15초 간격으로 같은 ID를 확인한다. 확정 또는 명확한 거부 이후에만 해당 기록을 제거한다. 최신 상태에서 새로운 행동을 임의로 골라 재전송하지 않는다.

## 좌석 인증 및 연결 복구

기존 암호학적 난수 토큰을 재사용한다. 서버에는 SHA-256 해시만 저장하고 상수 시간 비교(timingSafeEqual)로 인증한다. 클라이언트 토큰은 같은 origin의 기존 좌석 저장 키에 보관하며 URL·로그·상대 뷰에 넣지 않는다. 별도의 미확인 행동 기록에는 토큰을 복사하지 않는다. 방 코드만으로 차지한 좌석을 복원하거나 대체할 수 없다.

새로고침·브라우저 재실행 때 저장된 좌석을 읽어 인증한 뒤 최신 서버 상태를 받는다. 미확인 행동이 있으면 원래 요청을 확인하고, 정상 응답 이후 입력을 허용한다. 서버가 재시작해도 토큰 해시와 요청 기록이 외부 저장소에 있으므로 같은 좌석으로 복귀한다.

서버/네트워크 단절 중에는 `서버 재연결 중`을 표시하고 행동을 막는다. WebSocket과 HTTP 동기화는 지수 대기로 다시 연결하며, 정상 HTTP 대체 연결은 계속 사용할 수 있다. 실제 재연결 후에는 임시 조작 선택을 정리하고 서버 뷰 전체로 복구한다. 인증·방 없음·비호환 오류는 자동 재시도를 멈추고 원인을 표시하며 `연결 다시 시도`를 제공한다. 단순히 상대가 접속을 닫았다고 방을 지우지 않는다.

브라우저 저장소를 삭제했거나 다른 브라우저/기기를 사용하면 원래 토큰이 없으므로 방 코드만으로 좌석을 되찾을 수 없다. 이는 자리 탈취 방지를 위한 경계다. 같은 origin에서 실행되는 스크립트는 localStorage에 접근할 수 있으므로 이 방식을 HttpOnly 쿠키나 암호화된 저장소라고 표현하지 않는다.

## 저장 버전 및 기존 방

방 컨테이너 `version:1`, 엔진 `schemaVersion:"0.2.1"`, 네트워크 protocol/roomFormat1을 유지한다. 기존 v1에 `requests`가 없으면 읽은 객체에서 빈 목록으로 정규화하며 읽기만으로 Redis 원본을 다시 쓰지 않는다. 다음 정상 행동 때 추가 필드와 함께 저장한다. 기존 엔진/포도밭 저장 업그레이드는 기존 `parseSavedGame` 경로를 그대로 사용한다.

지원하지 않는 방 또는 엔진 스키마는 `ROOM_SCHEMA_UNSUPPORTED`로 거부하고 원본을 보존한다. 손상된 토큰·행동 기록·엔진 상태도 새 방으로 초기화하지 않는다. 향후 비호환 스키마는 명시적인 변환·검증을 추가하기 전까지 자동으로 추측해 복원하지 않는다. 구형 클라이언트의 requestId 없는 요청은 기존 revision 검증을 유지하지만 동일 요청의 성공 확인 기능을 제공하는 것은 아니다.

## 검증과 운영 범위

- `tests/core/upstash-rooms.test.ts`: 확정 후 Redis 응답 유실, 서로 다른 RoomStore의 동일/경쟁 요청, Undo 후 이전 요청 재전송, 기록 한도 이후의 오래된 revision, v1 읽기 무변경, 미래 형식 거부, 실제 배치된 포도/층/토큰과 장착 방패의 전체 저장 복원.
- `tests/deployment/server.test.mjs`: 실제 프로덕션 Node HTTP/WebSocket 서버를 재시작한다. 외부 저장이 확정됐지만 응답을 보내지 않은 시점에 SIGKILL하고, 빈 로컬 디렉터리와 변경된 서버 버전으로 시작한다. 이전 클라이언트는426으로 막고, 원래 토큰과 요청 ID로 복원해 자원·revision·저장 원문이 중복 변경되지 않았는지 확인한다.
- `tests/browser/online-recovery.spec.ts`: 확정 전/후 응답 유실, 재연결 중 입력 차단, 새로고침을 거친 같은 ID 복구, 두 브라우저의 같은 좌석 복귀, 느린 재시도, 비호환 오류 후 명시적 재시도.

외부 저장 테스트는 운영 Upstash와 분리한 REST 계약 모형이다. 실제 Node 프로세스 강제 종료를 시험하지만 Redis Lua 실행 엔진·실제 Upstash 계정·실제 Android/iPhone·외부 이동통신망을 시험했다고 주장하지 않는다. 실제 운영 방과 Redis 데이터는 변경하지 않는다.

## 이번 변경은 배포하지 않음

모든 이번 Push에는 `[skip render]`와 `[no-deploy]`를 넣는다. 전자는 Render 자체 자동 배포를 보류하고 후자는 기존 `Game release` 워크플로의 배포를 보류한다. 검사는 실행하되 운영 서비스를 재시작하거나 환경변수/저장소를 변경하지 않는다. 사용자가 이후 배포를 명시 요청하면 검증된 커밋과 실제 호환성을 확인한 뒤 기존 서비스에 반영한다.

근거: [Redis Lua 원자적 실행](https://redis.io/docs/latest/develop/programmability/eval-intro/), [Render 자동 배포 생략](https://render.com/docs/deploys#skipping-an-auto-deploy).
