# v0.2.2 공식 영지 보드 조사 및 데이터 명세

**2026-10-18 갱신:** 사용자 제공 도감으로 개인 영지1~30의37칸 전체 지형·눈을 등록하고 준비 화면에 연결했다. 최신 상태와 검토 한계는 [도감 등록 기록](boards/se-duchy-sheet.md). 아래 ‘2번만 등록/나머지 미확보’는 이전 단계 기록이다. 팀·솔로·샤토마 및 초소 특수 표시는 계속 별도다.

## 1. 조사 범위와 출처

확인일: 2026-10-17. 기준 자료는 `reference/CoB_Rulebook_285x210mm [28 pages] - 복사본 (2).pdf`이며 출처·SHA-256은 [rules/sources.md](rules/sources.md)를 따른다. reference에는 이 PDF 한 개만 있다. 프로젝트 내 src/app의 영지는 v0.1 데모이고 공식 보드의 근거로 사용하지 않는다. BGA 코드·이미지와 웹의 출처 미확인 보드는 사용하지 않았다.

PDF p.2–3의 구성품 사진과 본문, p.5·13–16·22의 번호 및 준비 설명을 대조했다. 작은 사진에서 일부 색·주사위 도상을 볼 수 있어도 전체 번호별 앞뒤 면과 모든 칸을 확정하기에는 자료가 불충분하다. 사진을 확대하는 것만으로 보이지 않는 면을 복원하지 않는다.

## 3. 칸 구성·숫자·구역·시작 성의 확인 수준

- 기본판 칸은 성·선박·광산·가축·건물·수도원에 대응하는 색과 주사위 눈을 가진다. 배치는 같은 색·눈, 기존 타일과 변 인접 조건을 사용한다(p.7).
- 같은 색으로 변이 연결된 칸이 구역을 이룬다. 한 보드 안에서도 같은 색의 서로 떨어진 구역은 다른 ID다. 도시의 크기·개수는 영지에 따라 다를 수 있다(p.8–9).
- 기본판은 원하는 성 칸에 시작 성을 놓는다. 1·2번은 중앙 6번 성을 권장하지만 필수 위치는 아니다(p.5, 9). 2번은 4개 성 후보 좌표와 중앙 권장 칸을 전사했고 나머지는 미확정이다.
- 팀 기본 면의 중앙 성, 숙련 면의 1 또는 6 성 선택이 설명되어 있다(p.15). 두 반쪽의 정확한 연결 위치는 별도 이미지가 필요하다.
- 솔로는 원하는 성 칸으로 시작한다(p.15). 샤토마는 카운티 카드의 성 칸에서 시작하므로 일반 개인 영지의 고정 시작 칸과 동일하게 모델링하지 않는다(p.22).
- 공식 2번은 전체 좌표·지형·눈·지역·성 위치를 공식 규칙서 p.2에서 전사했다(boards/se-base-2.md). 나머지 번호는 아직 전체 검증하지 못했다. 임의 반경 3 격자나 v0.1의 37칸·색 패턴으로 공식 데이터를 대체하지 않는다.

**실제 공식 칸 배치 데이터화: 1개(2번).** 존재·번호·분류·출처 메타데이터는 38개다. `VERIFIED_BOARD_DEFINITIONS`와 공식 선택 목록에는 2번만 들어 있다. 검토는 Codex가 단일 공식 도상을 시각 전사한 상태로, 별도 실물/사람 검수와 구분한다. 테스트용 4칸 그래프는 합성 fixture이며 공식 목록·게임·미리보기에 등록되지 않는다.

## 4. 데이터 구조와 검증

`src/game/boards`는 기존 v0.2.1 타입을 import해서 사용하며 수정하지 않는다.

| 파일 | 책임 |
| --- | --- |
| types.ts | 공식 목록, 불변 배치 정의, 증거, 선택·배정 계획, 미리보기 결과 |
| axial.ts | 6방향 좌표·키·인접 관계 |
| regions.ts | 같은 색 최대 연결 성분 및 구역 간 인접 그래프 계산 |
| validation.ts | 좌표·칸·주사위·지형·구역·시작 성·증거 메타데이터 검증 |
| catalog.ts | 번호별 존재 확인 목록과 검증 완료 배치 목록을 분리, 선택/미리보기 가드 |
| index.ts | 별도 보드 모듈 공개 진입점 |

- axial 방향은 `(1,0), (1,-1), (0,-1), (-1,0), (-1,1), (0,1)`이다. 보드 이미지의 위쪽 방향과 좌표 원점은 전수 입력 시 별도 기록한다.
- `BoardDefinition`은 미배치 설계도다. v0.2.1 `DuchyBoard`는 실제 플레이어 점유 상태이므로 섞지 않는다.
- `expectedCellCount`는 근거와 대조할 수 있도록 보드별 명시한다. 모든 보드에 37칸을 강제하지 않는다.
- 셀에는 ID, `(q,r)`, terrain, number, regionId를 기록한다. 각 구역에는 칸 목록과 인접 구역 목록을 둔다. 선언된 데이터가 계산된 최대 연결 성분·구역 경계와 정확히 일치하는지 검사한다.
- `deriveRegions`는 이미 입력된 색과 좌표로 연결 구조만 계산한다. 지형·숫자나 누락된 공식 칸은 생성하지 않는다.
- 시작 성은 허용 후보 목록과 권장 위치를 분리한다. `any-castle` 정책은 전체 성 칸과 후보 집합이 같아야 한다.
- 타입 검사는 외부 JSON 파싱을 대신하지 않는다. `validateBoardDefinition`은 타입이 지정된 정의의 구조 검증기이며 임의 JSON의 안전 파서나 공식성 인증기가 아니다.
- 검증 완료 표기에는 공식 번호, 검토자·날짜와 원본 경로·SHA-256·면 위치 증거가 필요하다. 구조 통과만으로 공식과 동일함을 증명하지 않는다. 수동 전수 대조를 통과한 자료만 별도의 검증 목록에 추가한다.

## 5. 플레이어별 서로 다른 보드와 후속 화면 연동

`BoardAssignmentPlan`은 플레이어별로 `official`(지정 ID) 또는 `random`(허용 ID 풀) 선택을 보관한다. 중복 허용 여부와 난수 seed를 별도로 둔다. 서로 다른 보드 선택은 각 플레이어의 boardId로 표현하고, 같은 공식 면을 여러 플레이어가 쓰는 것도 정책에 따라 허용할 수 있다.

무작위 배정 알고리즘은 아직 구현하지 않았다. 후속 구현에서는 검증 완료·모드 호환 보드만 후보로 만들고, 중복 불허 시 풀 부족을 오류 처리한다. 공식 이미지가 없는 현재는 임의 대체 보드를 배정하지 않아야 한다. 반환값 `ResolvedBoardAssignment`의 playerId/boardId/startingCastleCellId는 v0.2.1 PlayerConfig에 연결할 수 있다. 실제 엔진 연결은 하지 않는다.

미리보기 API는 검증되지 않은 경우 `unverified-geometry`, 모르는 ID는 `unknown-board`를 반환한다. 가짜 도면을 보여주지 않는다. 검증이 끝나면 좌표·지형·숫자·구역·시작 성 후보를 반환할 수 있다. HTML/SVG 렌더링은 아직 없다.

보드 하나의 데이터와 표시 좌표를 분리했으므로 후속 UI는 각 playerId별로 다른 설계도와 점유 상태를 사용해 모든 영지를 동시에 표시할 수 있다. 확대·드래그·레이아웃 설정은 보드 정의에 넣지 않는다. 팀 합성, 포도밭, 샤토마 등은 전용 어댑터를 검증한 뒤 지원하며 현재 일반 개인 보드 선택 목록에서는 제외한다.

## 7. 검증·후속 단계

```text
npm run test:boards
node node_modules/typescript/bin/tsc --noEmit
npm run lint
npm run build
```

테스트는 Node 내장 테스트 러너를 사용한다. 전용 tsconfig로 임시 디렉터리에 컴파일하고 실행 후 해당 임시 디렉터리만 정리한다. 새 패키지는 설치하지 않는다. 원본 소스·기존 빌드 디렉터리는 삭제하지 않는다.

검증 범위: 인접 대칭성·음수 좌표·6방향·안전한 정수, 중복 칸/좌표, 지형/눈/칸 수, 구역 연결·분할·참조·경계, 시작 성, 검증 증거, 공식 목록 및 미검증 데이터의 선택/미리보기 차단. 합성 fixture 통과는 공식 칸 배치의 정확성을 의미하지 않는다.

다음 단계 제안(자동 진행하지 않음): 공식 전체 면 이미지 확보 → 번호별 좌표/눈/색 수작업 전사 → 별도 검토로 전수 대조 → 구역·시작 성 검증 → 검증 목록 등록 → 선택·무작위 배정과 플레이어 보드 생성 어댑터 구현 → 기존 레이아웃 명세에 따른 미리보기·여러 보드 UI 연결.
