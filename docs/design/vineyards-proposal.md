## 2. 유지할 데이터 — C를 채택하자는 제안

- 보드: V01~V12/24칸 좌표·주사위·보너스와 층2/4/6을 조사 도식 그대로 사용한다. 별도 새로운 보드/칸/보너스를 창작하지 않는다.
- 덱: 조사표 R01~R51의 혼합 각3/동색 각1을 사용한다. 공식 실물 ID가 아닌 프로젝트 ID로 저장한다. 같은 seed에서 순서가 재현되어야 한다.
- 모든 플레이어는 같은 복원 보드로 시작한다. 공식 실물4개 전수 검증 완료로 표시하지 않는다.
- 기본 게임은6품종/51장. 품종 축소는 선택 설정이며 기본값 끔. 3인1색 제거→35장,2인2색 제거→22장. 선택은 게임 전에 공개하고 같은 구성에서 시작한다.
- 준비/공급 수2인3+1,3인3+3,4인6+3 및 단계 잔여 제거/보충, 시작 토큰/층 토큰/종료 표는 기존 조사 A규칙 그대로 유지한다.

**채택 요청:** C근거를 프로젝트 데이터로 사용하자는 제안이다. 이번 문서 작성만으로 카탈로그 등록이나 사용자의 최종 규칙 확정을 처리하지 않는다.

## 3. 미확인 데이터의 구체적인 보완안

### 3.1 2·3인 공급대 눈금 — 프로젝트 제안 P01

세 공급 위치를 왼쪽부터 **(1,4), (2,5), (3,6)** 으로 정한다. 어느 한 눈금만 맞으면 주사위1개로 해당 타일을 가져온다. 4인은 기존 숫자1~6별6곳을 유지한다. 상점은 주사위 획득 대상이 아니다.

이유: 원형 눈금에서 서로 반대인 두 값을 묶으면 어느 눈금에서든 한 공급 위치까지 보정 비용이0 또는1이다. 특정 공급 위치를 목표로 한 균등한 주사위의 최소 비용은 `[0,1,1,0,1,1]`, 평균2/3일꾼, 최대1. 인접 묶음(1,2)은 `[0,0,1,2,2,1]`, 평균1, 최대2다. 이는 해당 공급 위치에 타일이 남고 별도 효과가 없을 때의 산술 비교이며 전체 게임의 실제 평균 소비가 아니다.

세 위치 모두 무보정 확률2/6로 동일하다. 첫 보드 진입 눈금1/4와도 하나의 묶음으로 읽힌다. **이 배치가 공식 뒷면과 같다는 주장이 아니다.**

### 3.2 포도 보너스 수량 — 프로젝트 제안 P02

6품종 각각 **4개**, 총24개로 설정한다. 서로 다른6종 한 세트에서 플레이어별 시작 토큰1개를 무작위로 지급하고 나머지는 풀에 돌린다. 층을 완료하면 아직 풀에 남아 있는 토큰 중1개를 고른다. 같은 품종 여러 개를 가져갈 수 있으며 같은 연결 영역을 중복 점수화할 수 없다.

이유: 품종 대칭/총24를 보존한다.3층을 모두 채워도 플레이어당 시작1+층3=최대4토큰,4인 전체 최대16개이므로 기본 풀24개의 총량 고갈은 발생하지 않는다. 특정 품종4개가 소진되면 그 품종만 선택할 수 없다. 선택 품종 축소 시 해당 품종의4토큰도 제거한다. 축소 설정에서는 제거를 먼저 적용하고, 남은 품종 각1개 세트에서 시작 토큰을 나누어 제외된 색이 지급되지 않게 한다. 남은 풀은3인20개/2인16개, 각각 최대 수요12/8개보다 크다.

품종별4개는 **설계 선택이며 공식 확인 결과 D를 A로 승격하지 않는다.**

## 5. 행동 순서와 UI 초안

1. 자신의 주사위 선택 → 포도 공급대에서 합법 타일/일꾼 비용 강조 → 선택하면 보관2칸 확보 후 획득한다. 폐기가 필요하면 먼저 폐기 대상을 확인하고 취소 가능하게 한다.
2. 보관 포도 선택+주사위 선택 → 합법 이중 공간 강조 → 두 품종 방향을 프리뷰로 선택 → 공간을 터치해 확정한다. 방향 선택/확대/이동만으로 자원을 소비하지 않는다.
3. 첫 배치는 V01/V02만, 이후는 배치 타일과 변 인접·해당 이중 공간 전체 비어 있음·눈금 일치. 인쇄 공간을 가로질러 임의 두 칸을 골라 놓지 않는다.
4. 배치 확정 시 주사위/일꾼/보관 제거/두 칸 점유를 원자적으로 처리하고 **보너스2개 대기**를 만든다. 플레이어는 두 보너스의 처리 순서를 고른다.
5. 첫 보너스의 자식 타일 효과·추가 행동을 끝까지 해결한 후 남은 보너스로 돌아간다. 자식 효과가 부모의 나머지 보너스를 지워서는 안 된다. 불가능/불필요한 효과는 기존 포기 선택으로 개별 소모한다.
6. 그 배치의 두 보너스와 자식 효과를 끝낸 뒤 층 완성을 검사하고 미지급 층 토큰을 고른다. 중첩 포도 배치에서 먼저 완성 보상을 받은 층은 다시 주지 않는다.
7. 모든 필수 선택이 끝나면 기존 자동 턴 진행. 개인 영지 아래 독립 접기/펼치기 포도 패널, 다음 행동 안내는 작게 표시한다. 공용 보드 기존 공급처와 타일 디자인은 바꾸지 않는다.

번호/색상만으로 구별하지 않고 포도 품종 아이콘과 a/b 방향 표시를 함께 쓴다. 새 일러스트 제작은 이 초안에 포함하지 않는다.

## 6. 구현할 경우의 상태·검증 설계

- 확장 상태에 판정 버전 `project-vineyards-v1`과 `dataOrigin:reconstructed/custom` 구분을 저장한다. 보드 데이터/C복원 덱/P01 공급 눈금/P02 토큰 풀의 버전을 별도로 추적한다.
- 물리 타일 한 ID는 주머니/공급대/상점/보관/포도 보드/제거 중 한 위치만 갖는다. 보관에서 두 칸에 같은 물리 ID를 복제하지 않는다. 예약한 열쇠2칸의 표시 참조와 실제 소유권은 분리한다.
- 공통 보관 용량 계산은 일반 타일1+포도2≤3으로 검사한다. 일반 획득/검은 구매/무료 타일/포도 획득 **모든 입구**에서 같은 검사를 사용해야 하며 기존 `includes(null)`만 재사용하면 안 된다. 보관2칸이 반드시 인접해야 한다는 새 제한은 만들지 않는다.
- 보너스는 배치ID/칸ID/실행ID를 가지며 `pending/active/done/skipped`와 선택한 순서·자식 continuation을 저장한다. 각 자원/점수 지급은 해당 ID로1회만. 먼저 소모 표시 후 자식 액션을 열어 재전송을 막는다.
- 층은 별도 `completed/bonusClaimed/tokenId`로 관리한다. UI좌표로 완성을 판정하지 않고 Vxx 셀 목록으로 계산한다. 자식 배치가 두 층을 완성해도 각각1회만.
- 종료 점수는 품종별 연결 영역 크기를 내림차순 정렬해 토큰 개수만큼 선택한다. 공급/자원 반응과 분리된 최종 ledger에1회 기록한다.13초과 영역은 점수표 확장으로 숨기지 말고 데이터 무결성 오류로 거부한다.
- 온라인은 서버 RNG로 덱/토큰/공급 확정, 클라이언트는 선택ID/방향/액션만 제출한다. 좌석·revision·보관2칸·보너스ID·연결 영역을 서버가 검증한다.
- 구저장에는 포도 상태를 추가하지 않는다. 새 판정 버전 저장을 읽을 때 모든 타일/토큰 수량·두칸 예약·층 지급·부모/자식 대기 상태를 검증하며 임의 복구하지 않는다.
