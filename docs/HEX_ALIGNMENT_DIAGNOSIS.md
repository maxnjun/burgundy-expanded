# 육각형 정렬 오차 정밀 진단

측정일:2026-10-19 / 기준 커밋:`1cbfbe3`.
**진단만 수행했다. 이미지·렌더링·CSS·게임·정규화 스크립트를 수정하지 않았고 전체 테스트와 빌드도 실행하지 않았다.**

## 핵심 결론

셀과 clipPath, 이미지의 이론적 육각형은 일치한다. 인접90쌍의 공유 꼭짓점 차이는 **0 SVG 단위**다. 확인된 주된 화면 문제는 `.table-view .hex-cell polygon` CSS가 `stroke="none"`을 덮어써 **2 SVG 단위 테두리**를 다시 그리는 것이다. 그 위에 **1 CSS px 공통 격자선**이 있고 PNG 내부의 색상 테두리도 존재한다.

파생 PNG의 알파 경계는 세 종류가 완전히 같으며, 최대 내측 래스터 오차는0.977241336 PNG px =0.091616375 SVG 단위다. 따라서 확인된 수치상 CSS 테두리 영향이 알파 경계 오차보다 크다.

## 측정 조건과 단위

- 1280×1000 Edge/Chromium, devicePixelRatio=1, 브라우저 배율100%. 실행 중인 앱의 별도 격리 컨텍스트에서 TEST FIXTURE 영지를 측정했다. 사용자 브라우저의 저장/현재 판을 읽거나 바꾸지 않았다.
- 전체 보드 모드, 전체 배율1, 개인 영지100/160/200%. 전체 보드 모드의0.58 계수가 있으므로 표시100%가1 SVG 단위=1 화면 px라는 뜻은 아니다.
- `getScreenCTM`, `SVGPolygonElement.points`, computed style 및 실제 PNG 바이트를 측정했다. double 좌표와 DOM points의 float32 표현을 구분한다.
- PNG bbox는 `[left,top,right,bottom)`이며 오른쪽/아래를 제외한다. 알파≥128 경계 픽셀 중심 `(x+0.5,y+0.5)`에서 이상 육각형의 가장 가까운 변까지 수직거리를 계산했다. 양수=안쪽, 음수=바깥. 경계 픽셀은 상하좌우 중 알파<128 이웃이 있는 픽셀이다. bbox 외곽과 픽셀 중심을 혼동하면 약0.5px 차이가 생긴다.

## 2. 타일 영역·클리핑·변환

|항목|실측 속성/해석|
|---|---|
|자식 SVG|x=Cx−41.569219381653056, y=Cy−48, width=83.13843876330611, height=96|
|clipPath|`clipPathUnits="userSpaceOnUse"`, points 문자열이 셀 polygon과 완전히 같다. 타일마다 고유ID|
|g transform|`translate(0 2.735026918962575)`|
|image x,y|−7.735026918962575, −2.735026918962575|
|image width,height|115.47005383792515의 정사각형|
|preserveAspectRatio|`xMidYMid meet`|
|CSS transform|image/자식SVG/보드/측정한 조상 모두`none`|

위 g의 y 이동과 image의 음수 y가 상쇄된다. PNG 정사각형은 **보드 좌표에서(Cx−48,Cy−48)부터96×96**으로 표시된다. 파생 PNG1px는0.09375 SVG 단위다. 파생 육각형 폭886.8100134752651px가83.13843876330611 SVG 단위가 된다. 음수 image x는 정사각형의 투명 좌우 여백을 보정하는 공통 수식이며 종류별CSS 보정이 아니다.

실제 영지 URL은 `/tiles/estate/{type}.png?v=<output SHA 앞12자>`다. 공용/보관은 원본과source SHA를 쓴다. manifest와6파일 SHA256을 대조했으며 일치했다. 이번 측정에서 오래된 파생 이미지를 사용한다는 증거는 없었다.

## 5. 테두리 중복과 화면 대조 측정

`src/app/game-screen.css`에 다음 규칙이 남아 있다.

```css
.table-view .hex-cell polygon { fill-opacity:.78; stroke:#e5e4bc; stroke-width:2 }
```

CSS가 속성`stroke="none"`보다 우선하여 기초 셀 polygon의 computed style은 **stroke=rgb(229,228,188), stroke-width=2px(2 SVG 사용자 단위), fill-opacity=.78**였다. 별도`EstateGrid`는 **#e7dfbc,1px,non-scaling-stroke**이고 PNG 내부에도 색상 테두리가 있다. 별도SVG 타일 프레임은 꺼져 있지만 **셀 선＋공통 격자선＋PNG 그림 속 선의3층**은 실제 존재한다.

CSS는clipPath 안의polygon에도 매치되지만, SVG clipPath는 도형으로 클리핑하므로 stroke가 클립 영역을 넓히지는 않는다.

160%에서 기초 셀 선만 **임시DOM 대조용으로** 비활성화해 캡처하고 즉시 원복했다. 소스/이미지/저장에는 적용하지 않았다. 공유 선박 변 중점의25행×12열 측정창에서 **50개 픽셀이 달라졌고, 영향 열은x=391,392의2열**이었다.

|화면 좌표|정상 RGB|셀 선만 제외한 대조 RGB|
|---|---|---|
|(391,450)|(26,121,189)|(4,109,189)|
|(392,450)|(230,224,188)|(173,200,192)|
|(393,450)|(79,140,165)|(79,140,165)|

뒤에 그린 셀의stroke가 앞 셀의PNG 위를 덮는 순서 때문에 같은 알파를 써도 한쪽 선이 더 도드라질 수 있다. 공통1px 격자선은 대조에도 남는다. hover 규칙은stroke를3으로 바꾼다. hover 부분은 CSS 선언 확인이며 별도의 hover 화면 측정은 하지 않았다.

### 그림 내부 색상 선의 비대칭

각 변 중점에서 안쪽 법선을 따라 첫 불투명 색상과RGB 거리≤3인 색이 연속되는 길이를 측정했다. 위→오른쪽 위 변부터 시계방향이다. 이는 **동일 색상 구간 길이**이며 의미상의 전체 테두리 두께를 자동 판독한 값은 아니다.

|PNG|6변의 외곽 동일 색상 구간(PNG px)|
|---|---|
|castle|[9, 29, 20, 11, 10, 1]|
|mine|[3, 1, 3, 19, 25, 8]|
|ship|[1, 1, 3, 26, 40, 18]|
|estate/castle|[12, 36, 27, 14, 12, 1]|
|estate/mine|[5, 1, 4, 25, 33, 11]|
|estate/ship|[1, 1, 2, 35, 54, 26]|

그림 내부의 색상 선은 동일한 정육각SVG stroke가 아니다. 예를 들어 선박 파생의 왼쪽 세로 변에서는54px(5.0625 SVG 단위)의 같은 색 구간이 이어지고 오른쪽 위 변에서는1px다. 그림 속 선의 비대칭과 알파 경계의 좌표 차이는 구분해야 한다. 이번에는 이를 수정하지 않았다.

## 7. 가장 적은 수정으로 해결하는 방법 — 이번에는 미실시

1. 우선table-view용polygon CSS에서`stroke`/`stroke-width`를 제거하거나 일반 기초 셀에만`stroke:none`을 적용하고, 이미 있는`EstateGrid`의 단일1px 선으로 통일한다. hover/합법 칸 강조는 별도 조건으로 유지해야 한다. PNG 재변환보다 작은 변경으로 확인된1.856 CSS px 중복 요인을 없앨 수 있다.
2. 같은 선박 쌍/배율에서 재캡처한 뒤 남은 문제가 그림 내부의 비대칭 색상 선인지 판단한다. 이를 추가 확대/위치 보정으로 감추면 다시 그림 테두리를 자르게 되므로 현재 수치만으로 추가 크롭을 권하지 않는다.
3. 공통1px 격자선도 원하지 않는다면 PNG로 채운 셀의 변만 격자선에서 제외하는 안이 다음 후보다. 빈칸 경계와 합법 강조 검증이 추가로 필요하다. 이번에는 설계 제안만 한다.
